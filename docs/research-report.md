# Customer Support Desk Platform: Research Report

> **Where the code is.** The experiment scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

> **Status: protocol v0.2, results recorded (2026-11-23).** Questions, methods and the statistical plan were written down in v0.1 before the full experiments ran; v0.2 adds the results and logs every deviation in the [change log](#12-change-log). **Every ticket, customer, agent and workload in this report is synthetic (generated by `sdp.generator` / `sdp.textgen`); nothing was measured on a real support team.** All numbers below are copied from `results/summary.md`, which `experiments/summarize.py` generates from the raw per-run files in `results/`.

## Abstract

This study asks four things about a small local helpdesk built on the Python standard library: (E1) does its business-hours SLA calculator agree with an independent minute-by-minute reference on awkward calendars; (E2) how much does the agent-routing policy change SLA breach rate and workload imbalance in a simulated six-agent team; (E3) how well does token-based similarity find duplicate tickets as the threshold varies; (E4) what request rate does the server sustain on the loaded machine it was built on. Results on synthetic data only: (E1) 1,500 random calendars gave 7,369 comparisons across five functions and **no disagreement**, and four deliberately broken variants of the calculator were each caught (13% to 33% of the first 300 cases); the time-zone rules themselves were not independently checked and the IANA database was unavailable. (E2) In 144 simulated runs (16 paired seeds per cell) skills-weighted routing cut the first-response breach rate from 0.163 (round-robin) and 0.119 (least-loaded) to 0.049 at moderate load, and from 0.380 and 0.340 to 0.103 at heavy load, with a larger imbalance (Gini of assigned tickets 0.141 against 0.019 and 0.059); but this follows from the simulator's assumption that an agent without the ticket's skill is 1.8x slower: with that assumption removed skills-weighted routing was no better than round-robin and slightly worse than least-loaded (0.048, 0.050 and 0.038). (E3) On synthetic paraphrase pairs no method exceeded F1 0.69; same-topic tickets with different details were the dominant false positives; at the product's default threshold (cosine 0.6) precision was 0.70 and recall 0.33 for medium paraphrases. (E4) With one server process and a Python load generator on the same busy machine the median throughput was 46.5 requests/s with one client thread, 74.9 with four and 62.9 with eight, with no errors and a p95 latency of 64, 150 and 311 ms. None of this is a prediction for a real support team.

## 1. Research question

Is a business-hours-aware SLA calculator correct on awkward calendars (holidays, pauses, daylight-saving days); how much does the agent-routing policy change SLA breach rate and load imbalance in a small support team; how well can cheap token-based similarity find duplicate tickets and how sensitive is it to the threshold; and what request rate does the local server sustain for a modest request mix on the machine it was built on?

## 2. Hypotheses

- H1 (E1): The product's SLA calculator agrees exactly with an independent minute-by-minute reference on randomized calendars, including start times near daylight-saving changes, holidays, pauses and open-ended pauses; and the comparison is strong enough to notice deliberately introduced bugs.
- H2 (E2): Skills-weighted routing gives a lower SLA breach rate than round-robin and than least-loaded routing, at the price of a larger imbalance in work between agents; and least-loaded routing beats round-robin on breach rate when the team is heavily loaded. (These were expected to depend on the simulator's skill-mismatch penalty, so a scenario without the penalty is included.)
- H3 (E3): With a tuned threshold, TF-cosine similarity separates duplicate from non-duplicate ticket pairs well on light paraphrases (F1 above 0.9) but its recall falls as paraphrases share fewer words, and "same topic, different details" tickets are the main source of false positives.
- H4 (E4): The server handles a modest mixed workload at a few tens of requests per second on a loaded laptop-class machine without errors, with latency dominated by the queue page and the reports endpoint; throughput rises little with client concurrency because database work is serialised behind one lock.

## 3. Background

- Support desks usually express service levels as response and resolution targets measured in business hours, with the clock paused while the team waits for the customer; implementations differ in how they treat holidays and daylight-saving changes. This product's semantics are written down in the README and in `sdp/calendars.py`; they are one reasonable choice, not a standard.
- Assignment policies (round-robin, least-loaded, skills-based) are textbook queueing and dispatch ideas; the simulation here is a deliberately small model, not a validated queueing model of any real team.
- Near-duplicate detection by token overlap (Jaccard) and by term-frequency cosine similarity are standard baselines in information retrieval (see Manning, Raghavan and Schütze, 2008). Stronger methods (embeddings, learned matchers) are out of scope because they would need models or downloads.
- Confidence intervals are percentile bootstraps (Efron and Tibshirani, 1993); paired comparisons use a sign-flip permutation test with Holm's correction (Holm, 1979); the Wilson score interval (Wilson, 1927) is used for proportions.

## 4. Method

### 4.1 System under test

The implementation in this repository: Python 3.12 standard library, SQLite, `http.server`. The experiments use the same `Desk`, calendar, SLA, routing and dedupe code as the UI.

### 4.2 Environment

Machine metadata and the system CPU load before runs are stored in `results/*_meta.json` and quoted in the results. Windows 11, AMD64 (8 logical CPUs as reported by the OS), CPython 3.12.13 chosen by `uv`, no third-party packages, `zoneinfo` unavailable (no IANA data, so time zones came from the rule-based fallback). **The machine was shared with other jobs: the system CPU load read just before runs was 91% (E1 start), 56% to 100% with a median of 87% (E2 samples), 71% (E3 start) and 38% to 100% with a median of 63% to 80% across E4 levels.** Simulated outcomes (E1 to E3) do not depend on machine load; wall-clock timings, E4 throughput and latency do and are probably pessimistic.

### 4.3 Experiments and baselines

- **E1.** Reference implementation: `experiments/e1.py::Reference`. It walks time one minute at a time, converts each minute to local wall-clock time with `datetime.fromtimestamp(t, tz)` and checks the raw weekly windows, holiday dates and pause list. It shares no interval arithmetic with the product. It does share the time-zone object, so the *rules* of the zone are not independently verified by E1 (they are unit-tested against hard-coded transition dates for 2025 and 2026). Cases: random zone (the 18 fallback names plus two fixed offsets), weekly windows (0 to 3 per day, minute resolution, a bias to round times, closed days), 0 to 12 holidays (plus, for 40% of cases, a holiday within 5 days of the start, and for 25% one on a DST change date), start times (half uniform over 2025 to 2026, half within 3 days of a hard-coded DST change date), targets log-uniform up to 1.2 weeks of open time, pauses (40% of cases, 1 to 3 intervals, 15% of those open-ended). Functions compared: `add_business_seconds`, `business_seconds_between`, `next_open`, `sla.compute_due` and the inverse property `between(start, add(start, n)) == n`. Power check: four deliberately broken product variants (ignore DST, ignore holidays, window end inclusive, ignore pauses) are run on the first 300 cases.
- **E2.** Three arms (round_robin, least_loaded, skills_weighted) x three scenarios x 16 seeds, same seed means same arrivals, texts, customers, base work times and customer waits in every arm (per-ticket random streams). One team of 6 agents with overlapping skills, 8 business days (12 calendar days) per run; scenarios `moderate` (50 tickets per business day), `heavy` (70) and `moderate_no_skill_penalty` (50, mismatch slow-down 1.0 instead of 1.8). Duplicate detection, escalation and surveys are off. Tickets created in the last 20% of each run are excluded from time and breach measures (their outcomes are cut off by the end of the run; this was fixed before the runs). Metrics: first-response and resolution breach rates, share of tickets with any breach, median first-response time, Gini coefficient of work minutes per agent and of tickets assigned per agent, total work minutes.
- **E3.** Pairs from `sdp.textgen` (12 topics, three subject and three body templates each, slot values for order number, plan, device and error code, a synonym table of about 60 words). Positives: same topic and slots, different body template, second text paraphrased at strength 0.15, 0.40 or 0.70 (probability of replacing each word that has a synonym; above 0.5 also drops filler words). Hard negatives: same topic, different slot values. Easy negatives: different topics. 300 pairs per class, 10 repetitions with fresh draws; methods `jaccard`, `cosine`, `cosine_bigram`; thresholds 0.05 to 0.95 in steps of 0.05.
- **E4.** `python -m sdp serve` in its own process on 127.0.0.1 over a copy of a seeded synthetic database; a load generator process with 1, 4 or 8 threads sends a fixed mix (30% queue page, 25% ticket page, 15% API list, 10% API ticket, 5% reports, 10% internal note POST, 5% create-ticket POST) for 8 s after a 1.5 s warm-up; 5 repetitions per level, each with a fresh database copy and server. CPU load is read just before every run.

### 4.4 Independent variables

Calendar and case features (E1), routing policy and load scenario (E2), similarity method, threshold and paraphrase strength (E3), client concurrency (E4).

### 4.5 Metrics

As listed under each experiment. Times are in minutes; business minutes use each ticket's SLA calendar and exclude paused time.

## 6. Statistical plan

- **Replication:** E1: 1,500 random cases; E2: 16 seeds per cell; E3: 10 repetitions; E4: 5 repetitions per level.
- **Summaries:** means (E2, E3) or medians (E4) with percentile bootstrap 95% intervals (4,000 resamples over seeds, repetitions or runs).
- **Comparisons:** E2 uses paired differences by seed with a two-sided sign-flip permutation test (exact for up to 16 non-zero differences) and Holm correction over the three pairwise comparisons of each metric within a scenario. No other tests.
- **Effect sizes:** the paired mean differences and their intervals are the effect sizes; a statistically detectable but practically small difference is called small.
- **No silent exclusions:** no run was dropped. The only exclusion rule is the pre-declared censoring of the last 20% of each E2 run.
- **Negative results are results:** where a hypothesis is not supported, the discussion says so.

## 8. Discussion

**H1 (supported, with a scope limit).** Across 1,500 random calendars (7,369 comparisons: `add_business_seconds`, `business_seconds_between`, the inverse property, `next_open` and `sla.compute_due`) the product and the independent reference never disagreed, including 3,563 comparisons that start within three days of a DST change, 369 with an open-ended pause and 31 cases in which both agreed that the target was unreachable within the 14-day horizon. The harness is not vacuous: each of four deliberately broken variants (ignore DST, ignore holidays, window end inclusive, ignore pauses) disagreed with the reference on 13% to 33% of the first 300 cases. Limits: E1 compares against a reference that shares the time-zone object, so a mistake in the DST *rules* would be invisible to it; the rules have their own unit tests with hard-coded 2025 and 2026 transition dates, written from the author's knowledge of those dates. All zones went through the rule-based fallback or fixed offsets because the machine has no IANA data, so the `zoneinfo` path is untested here. A passing result shows agreement on these generated cases, not proof of correctness for every calendar.

**H2 (supported only under the simulator's skill-penalty assumption).** With the 1.8x slow-down for skill mismatches, skills-weighted routing lowered the first-response breach rate against both alternatives in both loaded scenarios (moderate: -0.114 against round-robin and -0.069 against least-loaded; heavy: -0.277 and -0.237; all Holm p about 0.0001) and cut median first response from 40 to 11 business minutes (moderate). It also did about 32% less total work (14,401 against 21,199 agent minutes) because it avoids mismatches, and it was less balanced: the Gini coefficient of assigned tickets was 0.141 against 0.019 (round-robin) and 0.059 (least-loaded), and of work minutes 0.107 against 0.073 and 0.065 (moderate). The work-minute imbalance is modest and partly by design (specialists receive the tickets only they can do quickly). Least-loaded beat round-robin by a smaller margin (-0.044 moderate, -0.040 heavy). When the penalty was removed, skills-weighted routing did not beat round-robin (-0.002, CI -0.009 to +0.005) and was slightly *worse* than least-loaded (+0.010, CI +0.005 to +0.015); a plausible reason is that concentrating tickets on the agents who hold a rare skill builds queues while others idle, but that explanation was not tested. Resolution breach rates were small everywhere (at most 0.015) because resolution targets are loose compared with handling times, so the breach story is mostly about first response. The honest reading: in this model, using skill information helps a lot *if* a skill mismatch is expensive and the tags that encode skills are reliable, and balancing load alone is a safer small gain otherwise. Whether skill mismatch is that expensive in a real team is an empirical question this report cannot answer.

**H3 (not supported as stated).** No method reached F1 0.9: the best F1 was 0.65 to 0.69 across methods and paraphrase strengths. Recall at a fixed threshold fell as paraphrase strength rose (cosine at 0.6: 0.44, 0.33, 0.19 for strengths 0.15, 0.40, 0.70) and the best threshold fell with it (Jaccard 0.2, 0.15, 0.1), as expected. Same-topic tickets with different details were the dominant false positives: at cosine 0.5 the false-positive rate was 0.348 on hard negatives and 0.000 on different-topic pairs. In the first repetition the mean cosine similarity of positives (0.510) was only modestly above that of hard negatives (0.417), because the tokens that distinguish "the same request" from "the same kind of request" (an order number, a plan name) are a small share of the text and are weighted like any other word; weighting rare or numeric tokens was not tried. Numeric thresholds are not comparable across methods (at 0.6 Jaccard flagged nothing). The product's default (cosine, 0.6) is a conservative operating point (precision 0.70, recall 0.33 at medium strength); the F1-optimal point on this data (cosine 0.3) has precision 0.54 and recall 0.90. Which is better depends on whether a spurious suggestion (an agent glances at a related ticket) costs more than a missed duplicate; the product only *suggests* and never merges automatically, so the default was left at 0.6. Because the text is synthetic and its paraphrases are easy, real recall is likely lower.

**H4 (partly supported).** No request failed (7,204 requests over 15 runs), and the median rates were 46.5, 74.9 and 62.9 requests per second at 1, 4 and 8 client threads. Latency was not dominated by the queue page: the reports endpoint was the slowest by far (median 122 ms at one thread against 10 to 19 ms for single-ticket and list requests) and the queue page was typical of the rest. Throughput rose by about 60% from one to four threads and did not rise further at eight (the intervals overlap: 52.9 to 82.6 against 59.4 to 67.6) while p95 latency doubled from 150 to 311 ms, which is consistent with database work serialised behind one lock and with the Python server and load generator competing for the same busy CPUs, but nothing was profiled, so the cause is not established. The system CPU load before runs ranged from 38% to 100%, which makes the run-to-run spread large (for example 52.9 to 82.6 requests/s at four threads).

**Practical guidance.** (1) Treat the SLA calculator as well exercised on generated calendars, and verify the time-zone path on a machine with IANA data before relying on zones outside the fallback list. (2) If a team's tickets carry reliable skill tags and a mismatch is costly, route by skills but watch the workload spread; if not, least-loaded is a safe default. (3) Keep duplicate detection as a suggestion; do not auto-merge on a lexical score. (4) For more than a handful of agents or any real load, expect to replace the single-connection SQLite and single process, and profile before deciding what to change. (5) None of this has been tested on real data.

## 9. Threats to validity

- **Everything is synthetic.** Arrival patterns, handling times, waiting behaviour, skill penalties, ticket text and CSAT scores are assumptions written by the author and not validated against any real support operation. E2 and E4 describe the simulator and this build, not a real team or a production deployment.
- **E2 depends on its assumptions.** The size of the skills-weighted advantage follows from the 1.8x skill-mismatch slow-down and from skill tags being assigned by keyword rules that always fire on the synthetic text. The no-penalty scenario shows what remains without the slow-down; other plausible assumptions (agents who are fast generalists, ticket mixes with few skill-bound tickets, interruptions, shifts, breaks) were not tested. One team of six agents and one calendar were simulated.
- **E1 shares the time-zone object with the product.** A bug in the DST rules of `sdp.tz` would be seen identically by both sides. The rules are covered by separate unit tests with hard-coded transition dates for 2025 and 2026 (US, EU and Australian-east rules) that were written from the author's knowledge of those dates, not downloaded. The IANA (`zoneinfo`) path could not be exercised because the machine has no IANA data; all zones in E1 went through the fallback or fixed-offset implementation.
- **E1 covers minute-aligned inputs.** Sub-minute timestamps are handled by the code but not by the reference. Calendars whose windows cross midnight are not supported by design.
- **E3 text is easy and artificial.** Paraphrases come from a 60-word synonym table and reuse the original template's vocabulary; real paraphrases are likely harder, so recall is optimistic. Hard negatives differ mostly in slot tokens (an order number, a plan name), which may be easier or harder than real near-misses. Thresholds that are best on this data should not be copied to real data.
- **E4 ran on a shared, busy machine** with the load generator and the server on the same host, one server process and one SQLite connection behind a lock. Latencies and rates are for that configuration only; the CPU load before each run is recorded and was high. No network, no TLS, no authentication and no large databases were involved.
- **Unexplained stalls in tiny harness runs.** Twice, in the unit test that runs E4 at tiny size (2 s windows), one connection stalled: once for about 10 seconds and once for a shorter, unmeasured time (throughput of that run fell to 11.9 requests/s). Neither happened in any of the 15 reported runs (largest p99 of any reported run: 473 ms), and 16 further tiny runs written for diagnosis (2 and 8 threads, 2 s each) showed none (largest p99 209 ms). The 10 s equals SQLite's busy timeout in this code, but that would normally surface as an error rather than a slow success; file locks or scheduling delays from other processes on the shared machine are candidates. It was not reproduced or diagnosed, so an intermittent stall in the server cannot be ruled out.
- **Small number of repetitions** (16 seeds, 10 repetitions, 5 runs) gives wide intervals for some cells; Holm correction is within, not across, metrics.
- **Simulator and product share code and the author.** The simulator exercises the real desk code, which is a strength for integration coverage, but it also means a conceptual error in the SLA semantics would be present on both sides of every experiment.
